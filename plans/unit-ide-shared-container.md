# Анализ: один общий IDE-контейнер на все юниты

Статус: **черновик для обсуждения** (архитектурный анализ, не план реализации).

## 1. Задача

Рассмотреть вариант: вместо IDE-сайдкара на каждый юнит — **один общий
контейнер с VS Code (code-server) на все юниты**, чтобы снизить потребление
памяти. Оценить плюсы/минусы, рассмотреть альтернативные редакторы и
альтернативные способы решить ту же проблему.

## 2. Текущее состояние

| Что | Где | Как устроено |
|---|---|---|
| Редактор юнита | IDE-сайдкар в **network namespace юнита**, порт [`IdePort`](../src/Unitman/Business/Utils/IdePort.php:18) 47000 | read-only для всех; `redaktorLink` появляется после подготовки, очищается при сбросе/пересборке |
| Ссылка на редактор | [`SsylkaServisaUtil`](../src/Unitman/Business/Utils/SsylkaServisaUtil.php:48) | `{scheme}://47000.{unit}.{project}.{publicAddress}` — proxy находит контейнер по поддомену |
| Редактор workspace | отдельный `ide`-контейнер `asdozzz/unitman-workspace-ide:latest`, `network_mode: service:workspace` | multi-root `workspace.code-workspace`, RW-том `workspace_app`, `mem_limit: 512m`, `read_only: true` |
| Права на редактирование | [`plans/unit-redaktor-prava-redaktirovaniya.md`](unit-redaktor-prava-redaktirovaniya.md:1) | `view` для всех / `edit` только автор / `locked` на защищённых ветках; режим вычисляется, enforcement планируется на уровне монтирования `:ro`/`:rw` и git-хуков |

Ключевые свойства текущей схемы, которые важно не потерять:

1. **`localhost` внутри IDE = сервисы юнита.** IDE делит network namespace
   с юнитом, поэтому из терминала IDE доступны `localhost:<port>` сервисов
   юнита. Порт 47000 зарезервирован, чтобы не пересекаться с сервисами.
2. **Изоляция файлов.** IDE видит только том своего юнита/workspace; режим
   `view`/`edit` реализуется монтированием `:ro`/`:rw`.
3. **Proxy-маршрутизация по поддомену.** Каждый IDE — отдельный контейнер
   со своим именем, proxy маршрутизирует 1:1.
4. **Жизненный цикл.** IDE-сайдкар создаётся/пересоздаётся вместе с юнитом
   (подготовка, пересборка, сброс, удаление) — без отдельного состояния.

## 3. Вариант «1 общий контейнер на все юниты»

### 3.1 Как он мог бы выглядеть

Один долгоживущий контейнер `ide-hub` на хосте раннера:

- смонтирован общий корень с файлами всех юнитов (см. §4.3 — это нетривиально);
- proxy маршрутизирует `{47000}.{unit}.{project}.{host}` → `ide-hub`, а hub
  внутри себя определяет, какой юнит запрошен (по поддомену/пути);
- code-server открывает нужный каталог через `?folder=...`.

### 3.2 Плюсы

| # | Плюс | Комментарий |
|---|---|---|
| 1 | Экономия RAM при многих запущенных юнитах | Нет N экземпляров Node/VS Code server. Основная экономия — по **отключившимся** пользователям: пер-юнитный IDE работает всегда, общий отдаёт память после отключения. Оценочно 30–50 % при активных сессиях и заметно больше при редких подключениях; требует замера |
| 2 | Меньше контейнеров | Быстрее подготовка юнита (не создавать/стартовать сайдкар), проще cleanup, одна точка обновления версии IDE |
| 3 | Общие настройки/расширения | Один образ, одна конфигурация для всех |

Диск при этом почти не экономится: слои образа и так общие для всех
контейнеров одного образа, per-юнит остаётся только writable layer и tmpfs.

### 3.3 Минусы (фундаментальные)

| # | Минус | Почему это серьёзно |
|---|---|---|
| 1 | **code-server однопользовательский** | Одна аутентификация, общие настройки/расширения/состояние, общие окна. Для сервиса с многими тестировщиками всё равно нужны per-user процессы → «1 контейнер» превращается в собственный supervisor процессов (по сути мини-Coder/Gitpod), т.е. сложность не исчезает, а переезжает в свой код |
| 2 | **Потеря network namespace юнита** | В общем контейнере `localhost:8080` неоднозначен: у двух юнитов веб-сервис может слушать один и тот же порт. Терминал IDE теряет прямой доступ к сервисам юнита на `localhost` — либо фича умирает, либо нужен свой per-unit прокси/SOCKS-слой |
| 3 | **Доступ к файлам** | Именованные тома нельзя динамически смонтировать в работающий контейнер. Варианты: (а) переход раннера с именованных томов на общий bind-mount корень — заметный рефакторинг раскладки; (б) доступ через docker socket (`docker exec cat`) — медленно, нет inotify, ломает редактирование; (в) NFS — новая инфраструктура |
| 4 | **Безопасность и права** | Один процесс видит файлы всех юнитов. Модель `view`/`edit`/`locked` переезжает с уровня монтирования (`:ro`/`:rw`) на уровень приложения; риск утечки между юнитами/проектами; компрометация hub = все проекты сразу. Подписанные per-unit ссылки сложнее enforced |
| 5 | **Изоляция сбоев** | OOM/утечка/зависший language server в hub роняет или деградирует сессии всех пользователей; общий inotify-лимит и CPU-контеншн между всеми открытыми проектами |
| 6 | **Proxy и жизненный цикл** | Нужен свой мультиплексор (поддомен → каталог + авторизация), обработка `?folder=`, юнит пересобирается/удаляется при открытом редакторе — stale watchers, удалённые каталоги |
| 7 | **Производительность не гарантирована** | VS Code server плодит per-window extension host'ы: при N активных пользователях память растёт почти линейно; Node event loop — единая точка CPU-контеншна; выигрыш только на «базе» per-instance и на отключившихся пользователях |

Вывод по варианту: **технически возможен, но решает проблему памяти ценой
изоляции, безопасности и заметного собственного кода, при этом экономия
не гарантирована и зависит от поведения пользователей.**

## 4. Альтернативные способы решить ту же проблему

### A. On-demand жизненный цикл IDE (рекомендуется в первую очередь)

IDE-сайдкар стартует **по первому клику** на `redaktorLink` и останавливается
после N минут неактивности. Остановленный контейнер не потребляет RAM.

- сохраняются все свойства текущей схемы (изоляция, localhost, proxy, права);
- захватывает большую часть экономии общего контейнера;
- нужно: workflow раннера «запустить/остановить IDE», обработка в proxy
  «IDE не запущен → разбудить» (503 → старт → retry), трекинг неактивности
  (последний запрос через proxy или опрос соединений);
- холодный старт — секунды, UX приемлем для просмотра кода.

### B. Облегчённый режим просмотра

Для read-only просмотра (основной сценарий юнита):

- отключить расширения/language server'ы/телеметрию в view-режиме;
- `files.watcherExclude` на `vendor/`, `node_modules/` и т.п.;
- снизить `mem_limit` сайдкара (512m → 256m для view).

Дёшево, делается настройкой образа/команды запуска, без изменения архитектуры.

### C. Monaco-просмотрщик во фронтенде unitman

Для сценария «посмотреть файлы юнита» встроить в фронтенд file tree +
[Monaco](https://microsoft.github.io/monaco-editor/), файлы отдаёт API раннера.

- **нулевая серверная стоимость**: stateless, рендер на клиенте, масштабируется
  горизонтально, нет per-unit контейнеров вообще;
- идеально ложится на модель прав из
  [`unit-redaktor-prava-redaktirovaniya.md`](unit-redaktor-prava-redaktirovaniya.md:1):
  авторизация в UseCase, `edit` через API только автору;
- минусы: нет терминала, tasks, расширений, LSP (можно добавить позже отдельным
  LSP-proxy); нужно написать UI;
- полный IDE (code-server) остаётся для автора юнита и для workspaces.

### D. Общий «hub» с per-session процессами (phase 2, только по замерам)

Один контейнер, внутри — процесс code-server на каждую пару (пользователь,
юнит), общий bind-mount корень файлов, свой auth-роутер, reaper неактивных
процессов. Компромисс между A и «1 контейнер»: экономия на контейнерах и
base-overhead, но всё ещё теряется netns-семантика `localhost` (или нужен
per-unit port mapping), и это заметный объём собственного кода.

### E. Другие редакторы — обзор

| Редактор | Вердикт |
|---|---|
| OpenVSCode Server (Gitpod) | Тот же класс, что code-server: per-instance, однопользовательский. Материального выигрыша нет |
| Eclipse Theia | Похоже на VS Code server: backend на браузерную сессию. Мульти-тенантности из коробки нет |
| Zed | Нет стабильного веб-клиента — не подходит для доставки в браузере |
| Gitpod / Coder / Eclipse Che | Полноценные платформы workspace'ов: конфликтуют с собственным жизненным циклом юнитов unitman, тяжёлые |
| JetBrains Projector/Gateway | Тяжело, лицензирование, per-project IDE — нет |
| VS Code Tunnel | Требует локальный VS Code и MS-аккаунт у пользователя; интересно только авторам, не решает задачу «посмотреть в браузере» |

Смена редактора сама по себе проблему не решает: узкое место — **модель
«один инстанс IDE на юнит»**, а не конкретный продукт.

## 5. Workspaces

Для workspaces общий IDE **не рекомендован** в любом виде: там RW multi-root
редактирование одним владельцем — per-workspace изоляция (том, сеть, права)
соответствует семантике задачи. Экономия возможна только через A (старт по
клику на `ideLink`, стоп по неактивности) — применимо тем же механизмом.

## 6. Рекомендация

1. **Не делать** «1 контейнер на все юниты» в лоб: минусы §3.3 перевешивают,
   экономия не гарантирована.
2. Сделать **A (on-demand старт/стоп IDE)** + **B (облегчённый view-режим)** —
   это закрывает проблему памяти без потери свойств архитектуры.
3. Рассмотреть **C (Monaco-просмотрщик)** как целевое решение для сценария
   просмотра файлов юнита: нулевая серверная стоимость + естественная
   интеграция с планируемой моделью прав.
4. **D** держать как запасной вариант, если замеры (§7) покажут, что A+B
   недостаточно.
5. Workspaces — без изменений (опционально тот же on-demand механизм).

## 7. Что измерить перед решением

По образцу [`plans/memory-baseline-protocol.md`](memory-baseline-protocol.md:1):

1. Пик одновременно **запущенных** юнитов на раннере (остановленные контейнеры
   RAM не потребляют — проблема только в конкурентно запущенных).
2. Сколько пользователей реально открывают `redaktorLink`, как долго держат
   вкладку (телеметрия proxy: количество активных соединений на 47000).
3. Фактическое потребление IDE-сайдкара: `docker stats` по контейнерам IDE
   в view-режиме и с расширениями; вкладка расширений/language server'ов.
4. Оценка экономии A: доля времени, когда IDE запущен, но соединений нет.

## 8. Следующие шаги (если решение принято)

1. Замер по §7 → подтвердить, что проблема памяти реальна и где.
2. Прототип A: workflow раннера `ZapustitIdeUnita`/`OstanovitIdeUnita`,
   обработка «будилки» в proxy, idle-таймаут.
3. Конфиг B: облегчённый view-образ/флаги запуска code-server.
4. Отдельный план на C (Monaco): контракт file-API раннера, авторизация,
   UI-компонент.
