# Протокол baseline-замеров памяти Unitman

Документ описывает, что нужно подготовить и какие срезы снять **до** любых
изменений. Без этих данных нельзя ни доказать эффект оптимизаций, ни выбрать
безопасные размеры пулов.

Замер — это не одна команда, а четыре независимых среза:

1. инвентаризация процессов и конфигурации;
2. профиль в состоянии покоя после прогрева;
3. профиль под нагрузкой;
4. дрейф памяти за полный цикл эксплуатации стенда.

Сроки в документе не указываются: длительность определяется доступностью
стенда, наличием тестовых данных и числом повторных прогонов, а не самой
методикой.

## 1. Что нужно подготовить

### 1.1. Стенд

- Запущенный production-подобный стек: `docker compose -f dc.mvp.yml up -d`
  (важно: `APP_ENV=prod`, `PHP_OPCACHE_ENABLE=1`, без xdebug в идеале — но
  baseline снимается на **текущем** образе, даже если xdebug там есть).
- Запущенный RoadRunner: `rr serve` и `php bin/console app:jobs start`
  (см. [`Makefile`](Makefile:9)).
- Работающие зависимости: PostgreSQL, Redis, Beanstalk, MinIO, Centrifugo,
  Temporal.
- Доступ к Docker socket и возможность выполнять команды внутри контейнера `web`.

### 1.2. Доступы и инструменты

- shell внутри `web`: `docker compose -f dc.mvp.yml exec web sh`;
- `ps`/`/proc`, `awk`, `curl`, `php`;
- `docker stats` на хосте;
- Prometheus/Grafana из [`dc.tools.yml`](dc.tools.yml:32) — опционально,
  но дашборды `rr_http`, `rr_jobs`, `rr_temporal` уже есть в
  [`.docker/grafana/dashboards`](.docker/grafana/dashboards/rr_http.json);
- нагрузочный инструмент: k6, `hey` или `ab` (k6 удобнее для сценариев
  с разными payload).

### 1.3. Тестовые данные

- аккаунт с `ROLE_ADMIN` и валидный JWT: `POST /api/login`
  (`json_login`, см. [`config/routes.yaml`](config/routes.yaml:2));
- проект и юнит для read/write сценариев (или разрешение создавать их на стенде);
- токен прогресса для `saveSteps`: его регистрирует PHP перед стартом workflow
  ([`RunnerApi::zaregistrirovatProgressToken()`](src/Runner/Api/RunnerApi.php:75)).
  Для нагрузочного теста токен можно создать напрямую в Redis, не запуская
  реальную сборку:

  ```sh
  # формат совпадает с RunnerProgressKvStorage::zaregistrirovat()
  redis-cli --user "$REDIS_USER" --pass "$REDIS_USER_PASSWORD" --no-auth-warning \
    SET "runner.progress.token.loadtest-1" "$(date +%s)" EX 7200
  ```

- `RUNNER_CALLBACK_SECRET`: если он задан, нагрузочный скрипт должен считать
  `X-Runner-Signature`; если пуст, подпись не требуется
  ([`RunnerCallbackSignatureChecker`](src/Runner/Infra/Service/RunnerCallbackSignatureChecker.php)).
- большой zip для теста загрузки: файл до `MEDIATEKA_MAX_FILE_SIZE`
  (по умолчанию 200 МБ). Сигнатура проверяется по первым 4 байтам, поэтому
  можно собрать файл из случайных данных с корректным заголовком.

## 2. Срез 1. Инвентаризация процессов и конфигурации

Цель: подтвердить фактическое число PHP-процессов и их RSS, а также текущие
настройки PHP/OPcache.

### 2.1. Процессы и RSS

Alpine/BusyBox `ps` не всегда поддерживает `--sort`, поэтому надёжнее читать
`/proc`:

```sh
for d in /proc/[0-9]*; do
  pid=${d#/proc/}
  cmd=$(tr '\0' ' ' < "$d/cmdline" 2>/dev/null)
  [ -z "$cmd" ] && continue
  case "$cmd" in
    *"rr serve"*|*"bin/console"*|*"public/index.php"*)
      rss=$(awk '/VmRSS/{print $2}' "$d/status" 2>/dev/null)
      hwm=$(awk '/VmHWM/{print $2}' "$d/status" 2>/dev/null)
      ppid=$(awk '/^PPid:/{print $2}' "$d/status" 2>/dev/null)
      echo "$pid $ppid ${rss:-0} ${hwm:-0} $cmd"
      ;;
  esac
done | sort -k3 -n -r
```

Снимок нужно сохранить целиком в `plans/memory-baseline/processes.txt`.
Дополнительно:

```sh
# сколько всего PHP-процессов
for d in /proc/[0-9]*; do
  cmd=$(tr '\0' ' ' < "$d/cmdline" 2>/dev/null)
  case "$cmd" in *php*) echo "$cmd" ;; esac
done | sed 's/ .*//' | wc -l

# агрегат по контейнерам
docker stats --no-stream

# лимиты и настройки
docker compose -f dc.mvp.yml exec web php -i \
  | grep -E 'opcache|memory_limit|jit|realpath_cache|assertions'
docker compose -f dc.mvp.yml exec web php -m > plans/memory-baseline/php-extensions.txt
```

### 2.2. Конфигурация RoadRunner

Зафиксировать:

- содержимое [`.rr.yaml`](.rr.yaml:1) с подставленными переменными;
- значения `RR_HTTP_NUM_WORKERS`, `RR_JOBS_NUM_WORKERS`, `RR_TEMPORAL_NUM_WORKERS`
  и всех `process_num` у фоновых задач;
- версию RoadRunner: `rr --version` и `docker compose ... exec web rr --version`.

### 2.3. Метрики рантайма

```sh
curl -s http://localhost:2112/metrics | grep -E '^rr_' \
  > plans/memory-baseline/rr-metrics.txt
curl -s http://localhost:9091/metrics \
  > plans/memory-baseline/temporal-metrics.txt
```

Если Prometheus уже поднят, сохранить снимок `rr_http_workers_memory_bytes`
и аналогичных метрик по Jobs/Temporal за последние сутки.

## 3. Срез 2. Профиль в состоянии покоя

Условия:

- стек поднят и полностью прогрелся;
- нет активных сборок, загрузок и вебхуков;
- фоновые задачи отработали хотя бы один полный цикл `getDelay()`.

Действия:

1. Снять снимок `/proc` из раздела 2.1 три раза с интервалом, достаточным
   для завершения текущих итераций фоновых задач, и сохранить как
   `idle-1.txt`, `idle-2.txt`, `idle-3.txt`.
2. Зафиксировать `docker stats --no-stream` для каждого снимка.
3. Зафиксировать количество рестартов воркеров (по логам RoadRunner или
   метрикам supervisor).
4. Отдельно посчитать RSS по ролям: HTTP, Temporal, Jobs, фоновые сервисы.

Ожидаемо: число процессов соответствует конфигурации; разброс между снимками
не превышает нескольких процентов. Если разброс большой — есть утечка или
незавершённые задачи, это отдельный результат замера.

## 4. Срез 3. Профиль под нагрузкой

### 4.1. Сценарии

| Сценарий | Что проверяем | Payload |
|----------|---------------|---------|
| `saveSteps-small` | частый прогресс, троттлинг, Centrifugo | 10 шагов |
| `saveSteps-medium` | декодирование JSON, KV | 500 шагов |
| `saveSteps-max` | пик памяти на предельном размере | около 2,5 МБ |
| `units-list` | чтение списка юнитов | параметры фильтра |
| `unit-create` | запись и событие | минимальный набор полей |
| `mediateka-upload` | потоковая загрузка | 50 МБ и 200 МБ |

### 4.2. Требования к прогонам

- каждый сценарий — не менее трёх прогонов для устойчивого p95;
- перед каждым прогоном — стабилизация стенда и снятие idle-снимка;
- во время прогона фиксировать `docker stats` и `/proc` каждые 10–15 секунд;
- после прогона — снять `VmHWM` (пиковый RSS) по каждому процессу: именно
  он показывает, насколько близко воркер подошёл к `max_worker_memory: 100`.

### 4.3. Что сохранить

- p50/p95/p99 и RPS по каждому сценарию;
- пиковый RSS по ролям и суммарный;
- число рестартов воркеров во время прогона;
- ошибки и таймауты;
- лаг очередей Beanstalk и Temporal после прогона.

## 5. Срез 4. Дрейф памяти

Цель: понять, растёт ли RSS между рестартами и как быстро.

- Наблюдение ведётся за полный цикл эксплуатации стенда, включающий
  периодические фоновые задачи, вебхуки и хотя бы одну сборку/запуск юнита.
- Снимки `/proc` и `docker stats` снимаются регулярно в течение цикла.
- Строится график RSS по ролям и отмечаются рестарты по `max_worker_memory`.

Результат: ответ на вопрос, является ли рост памяти утечкой или штатным
накоплением кэшей, и какой `max_worker_memory` безопасен.

## 7. Критерии готовности baseline

- [ ] Снимок процессов воспроизводится дважды с расхождением менее 5 %.
- [ ] Зафиксированы настройки PHP, OPcache и все размеры пулов.
- [ ] Для каждого ключевого эндпоинта есть p50/p95/p99 минимум по трём прогонам.
- [ ] Зафиксированы пиковый RSS и число рестартов под нагрузкой.
- [ ] Есть профиль дрейфа за полный цикл эксплуатации.
- [ ] Данные сохранены в `plans/memory-baseline/` и приложены к плану.

## 8. Что можно не делать на первом проходе

- Полноценный профиль CPU: задача — память, CPU понадобится только для
  проверки, что снижение числа воркеров не увеличило задержки.
- Тонкий анализ аллокаций через xhprof: сначала нужны макроданные по процессам.
- Нагрузку на все эндпоинты: достаточно шести сценариев из раздела 4.1,
  остальные проверяются выборочно после изменений.
