# WS-2: шифрование токенов репозиториев at rest

## Что изменилось

Токен доступа к репозиторию не хранится в открытом виде ни в `Repo`-агрегате,
ни в событиях, ни в проекции `repo_list`.

- Шифр: AES-256-GCM (`UmeetShifrovatSekrety` / `PersonalTokenOpenSslShifr`).
- Формат: `base64(nonce[12] || tag[16] || ciphertext)`.
- AAD: строковый `repoId`. Перестановка шифротекста между репозиториями
  не проходит проверку GCM.
- Ключ: `LICHNIY_TOKEN_CREDENTIALS_KEY` — base64 от 32 байт. Тот же ключ,
  что и у личных токенов хранилищ. **Без ключа данные не восстановить.**
- `tokenHint`: последние 4 символа токена, для токенов короче 8 символов —
  пустая строка. Необратим, используется в публичном DTO WS-1.

События `RepoWasAdded` / `CredentialsOfRepoWasChanged` содержат только
`tokenCipher` + `tokenHint` и не содержат `token`.

## Обратная совместимость удалена

Legacy-формат с открытым `token` больше не поддерживается:

- нет upcaster'а и чтения старых событий;
- нет opt-in миграции и команды `app:security:encrypt-repo-tokens`;
- нет Doctrine-миграции `Version20261126170000`.

База создаётся с нуля по актуальным миграциям. Тестовые данные не переносятся.
Для реальных данных единственный безопасный путь — восстановление из бэкапа
с последующим повторным добавлением учётных данных через UI; переписывать
исторические payload'ы вручную нельзя.

## Изменение учётных данных (write-only)

`POST /api/repo/changeCredentials`:

- `token` не передан, `null` или пустая строка — текущий секрет сохраняется.
  Если URL тоже не изменился, событие не порождается.
- `token` непустой — секрет шифруется, hint обновляется, порождается событие.

Это контракт для write-only UI WS-5.

## Ротация и потеря ключа

- Автоматический `down()` невозможен: обратное преобразование шифротекста в
  открытый вид требует ключа.
- При потере ключа восстановление возможно только из внешнего бэкапа БД.
- Ротация ключа не поддержана online: после смены ключа токены репозиториев и
  личные токены нужно добавить заново через UI.

## WS-9 handoff

Ключевой материал приходит из `EncryptionKeyProvider` (`KeyPurpose::REPO_TOKENS`),
а не из прямого `getenv` в потребителе. Контракт `UmeetShifrovatSekrety` и формат
шифротекста при этом не меняются.
